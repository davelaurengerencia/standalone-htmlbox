# HTMLBox — Orden de implementación

Orden de arriba hacia abajo, sin numerar a propósito — así reordenar es mover una línea, no renombrar archivos ni arreglar referencias cruzadas cada vez que cambia la prioridad. Marcar `[x]` cuando el trabajo de esa línea esté implementado (el archivo de la spec en sí también pasa a `-IMPLEMENTED.md` cuando corresponda — eso sigue siendo la fuente de verdad real, esta lista es solo el mapa de progreso).

- [ ] `htmlbox-spec-auth-centralizado.md` — **URGENTE, primero de todos.** Reemplaza el parche de 3 capas de la sesión del 2026-08-28 (host detection vía headers entre workers, que resultó ser la causa de fondo de todos los bugs de login de esa sesión) por un worker `auth.<dominio>` dedicado que el browser toca directo — sin cross-worker hops, sin heurística de headers. Bloquea producción: el login real hoy no funciona en dev de forma confiable.
- [ ] `htmlbox-spec-wfp-consolidacion.md` — núcleo (§1, §2, §4: activar el binding R2 ya declarado y sin usar, `redeployBoxWorker()`, `wrapper.mjs` leyendo directo de R2). Sin dependencias con nada de esta lista — no toca `dataApi.js`, no toca Turso, no toca IA. Ganancia inmediata y medible (elimina el round-trip a control-plane para boxes públicos).
- [ ] `htmlbox-spec-wfp-consolidacion.md` — Variables y Secrets (§3). Reusa `redeployBoxWorker()` del punto anterior — por eso va justo después, no antes.
- [ ] `htmlbox-spec-box-flows-backend.md` — boxes con backend visual (Flow Engine) en vez de Worker escrito a mano. Depende de `htmlbox-spec-wfp-consolidacion.md` (reusa `redeployBoxWorker()`, Variables/Secrets, y el `worker.js` sirviendo HTML directo de R2 — se combinan en un solo archivo generado). No depende de tablas-reales/IA, puede ir en paralelo con esos.
- [ ] `htmlbox-spec-sivostudio.md` — PROTOTIPO AISLADO, sin auth: proyecto nuevo `packages/sivostudio` (separado de portal/control-plane, namespace de WFP propio) donde un botón "Crear box" aprovisiona de una vez un Worker real con bindings + flow-engine, y App Studio + Flow Editor conviven contra ese worker desde el día 0. Sin dependencias duras con el resto de la lista — toma prestado el patrón de worker.js de box-flows-backend pero implementa su propia versión mínima. Auth queda pendiente para si esto pasa de experimento a algo real.
- [ ] `htmlbox-spec-tablas-reales.md` — fundacional para el resto. Columnas SQL reales en vez de `data_json`, `PRAGMA table_info` como fuente de verdad. Se implementa y verifica aislado de IA y de WFP.
- [ ] `htmlbox-spec-provisioning-lazy.md` — depende de tablas-reales (`ensureTableReal` es un punto de disparo del aprovisionamiento). Con WFP ya implementado, el hook nuevo que agrega ("al terminar de aprovisionar Turso → `redeployBoxWorker(reason: 'turso_provisioned')`") es una llamada a algo que ya existe, no hay que construir el mecanismo de deploy desde cero acá.
- [ ] `htmlbox-spec-ai-analyze-robusto.md` — depende de tablas-reales (necesita columnas reales para que `unique`/`references` signifiquen algo). Con Variables y Secrets ya implementado, puede sumar el atajo "detecté `external_integration` → ¿agregás la key acá?" sin inventar dónde guardarla.
- [ ] `htmlbox-spec-ai-tool-loop.md` — el más complejo, depende de tablas-reales, provisioning-lazy y ai-analyze-robusto funcionando los tres. Se verifica al final, con todo lo demás ya estable.
- [ ] `htmlbox-spec-import-archivos-locales.md` — depende de ai-analyze-robusto (mismo paso de análisis, extendido). Puede ir en paralelo con ai-tool-loop si hace falta — no depende de ese.
- [ ] `htmlbox-spec-box-devs-zip-upload.md` — el v0 de Box Devs: crear el proyecto en local, subir un ZIP, queda deployado. Depende de wfp-consolidacion (reusa `deployBoxWorker()`/`redeployBoxWorker()`). Tiene un punto bloqueado hasta confirmar contra la documentación real de Turso (§4 de esa spec — cómo importar un `.sqlite` existente vía su API programática) — no arrancar la implementación de esa parte sin esa confirmación.
- [ ] `htmlbox-spec-box-devs-preview.md` — el editor en el navegador con preview descartable. Camino alternativo/posterior al ZIP, para ediciones rápidas sin volver a zippear — no reemplaza al anterior, lo complementa. Depende de wfp-consolidacion igual que el anterior. Es la de menor urgencia de las 9.

## Por qué WFP va primero

WFP (los dos primeros puntos) y la capa de datos/IA (el resto) tocan partes del código que casi no se cruzan: `wfpDeployer.js`/`wrapper.mjs`/`runtime/worker.js` por un lado, `dataApi.js`/`boxSchema.js`/`aiProvider.js` por el otro — se pueden trabajar en paralelo sin pisarse. El único punto real de esta lista donde SÍ se tocan es `ensureBoxProvisioned()` (provisioning-lazy) llamando a `redeployBoxWorker()` (WFP) — y ese punto queda más simple si WFP ya está implementado cuando se llega ahí, en vez de tener que construir ambos a la vez.

## Regla general para verificar cada punto

Antes de dar por cerrado cualquier punto: correr sus tests contra Turso/Cloudflare REAL (no mock) para las partes que tocan SQL o la API de deploy — mismo criterio ya usado en las specs de WFP y app-users (verificado a mano, no solo "los tests unitarios pasan"). Las partes que tocan Gemini (ai-analyze-robusto, ai-tool-loop) pueden mockear la llamada HTTP en la mayoría de los tests, pero necesitan al menos un smoke test manual contra la API real antes de cerrarse (mismo patrón que `scripts/smoke-wfp.mjs` ya usó para WFP).
